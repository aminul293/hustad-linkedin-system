# Hustad Outreach

The LinkedIn new-business system for Hustad Companies, as one page with five tabs: the cold DM
desk Eric works from during his 11:05 to 12:05 block, the reply center, the posting calendar with
designed assets, the newsletter, and the article pipeline. The pipeline builds all of it; the
worker publishes the posting side through the official LinkedIn API; every DM stays human, by rule
and by platform reality.

---

## Read this before you push anywhere

**This repository's `data/` directory holds personal data about several thousand real people**:
names, job titles, employers and LinkedIn profile URLs from Eric's connection export, plus a CRM
export with account names and deal values. The desk page embeds that data directly in its HTML.

`.gitignore` keeps all of it out of git. Nothing in `data/raw`, `data/work`, `data/out` or the
built `site/index.html` is ever committed. Only `data/sample/`, which is synthetic, is tracked.

That means **a public GitHub Pages deploy of this repo publishes nothing sensitive, because the
built page is not in the repo.** It also means deploying the real desk needs a host you control
access to. See [docs/DEPLOY.md](docs/DEPLOY.md); the short version is that this is an internal tool
with PII and it needs authentication before it goes on the open internet.

If you ever find yourself adding an exception to `.gitignore` for something under `data/`, stop and
read [docs/PRIVACY.md](docs/PRIVACY.md) first.

## Run it in two minutes, with no real data

```bash
make setup      # pip install pandas, openpyxl
make sample     # generate synthetic records and build the page from them
make check      # verify the invariants hold
make serve      # http://localhost:8000
```

`make sample` writes 60 invented people at invented firms in the exact schema the real plan uses,
so the whole front end runs without anyone's data ever being on your machine.

## Run it with real data

If this arrived as a zip, there is a `PRIVATE_DO_NOT_COMMIT/` folder next to the repo folder. Copy
its three files into `data/work/` first. They are the client map for Gate G2, the change logs, and
the most recent day's storm openers. They are deliberately outside the repo so that dragging the
repo folder into GitHub's web uploader, which ignores `.gitignore`, still publishes nothing.

Then put the LinkedIn export and the CRM opportunity export in `data/raw/` and:

```bash
make plan       # classify, score, select, schedule, write copy, level the calendar
make check
make site       # build site/index.html
```

Set `HUSTAD_DATA=/some/path/outside/the/repo` to keep real data out of the working tree entirely,
which is the right call on a shared machine.

## How Data Storage & Updates Work (Production & Local)

Data in the system gets updated in two distinct ways:

### 1. Daily Activity Updates (Outreach & Replies)
As Eric uses the desk page during his daily outreach hour:
- **Instant Action Logging:** When he clicks "Sent", "Replied", or "Skip" on any contact card, the status is immediately saved to browser `localStorage` for zero UI latency.
- **Supabase Cloud DB Sync:** Background API `/api/sync/send` upserts records to the **Supabase PostgreSQL database** (`send_log` table) for multi-device sync across laptop, mobile, and desktop.
- **Sequence Protection:** If a contact is marked as "Replied", the system automatically halts all future follow-up touches for that person across all devices.
- **Persistence:** Because action logs survive page reloads and rebuilds, Eric never loses track of who has been contacted.

### 2. Periodic/Monthly Data Updates (New Contacts & Deals)
When you upload a new LinkedIn `.zip` or CRM `.xlsx` file through the uploader (`http://localhost:8765/upload`):
- **Overwrites Raw Files:** The server safely overwrites the old raw CSV files in `data/raw/` on the server disk.
- **Discovers New Connections:** `classify.py` parses the new LinkedIn archive, identifies any newly added connections, tiers them, and updates `master_contacts.csv`.
- **Merges CRM Pipeline:** `scale_plan.py` matches new CRM sales opportunities to existing companies so active deal accounts get proper outreach priority.
- **Re-generates Desk:** The build process creates an updated `site/index.html` containing the new contact queue while preserving all past send logs from Supabase.

*Production Storage Summary:* Sent actions & replies live in **Supabase Cloud PostgreSQL**. Raw contact archives live on the **Server File System**.

## The five rules

They are enforced in code, not just written down, and `make check` fails the build if one breaks.

1. **Hustad does not do new construction.** Only buildings that already stand. A groundbreaking or a
   topping out is a new building getting its roof and is never used as an opener, however recent.
2. **Nothing acts on LinkedIn.** The official data export is the only ingestion path and every
   message is sent by a human by hand. No bots, no scraping, no browser automation, ever.
3. **Past employment at a current client is Eric's own opener**, never an internal handoff.
4. **No two people at one firm open on the same sentence.** Colleagues compare DMs.
5. **No figure without a source.** Any post carrying a cost or lifespan number must cite a
   FACTS entry, and the roadmap's banned claim phrases fail the build.
